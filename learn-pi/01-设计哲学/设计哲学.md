# 设计哲学

Pi 的哲学可以压成一句话：

> **激进可扩展（aggressively extensible），所以不必替你规定工作流。**

出处：`packages/coding-agent/README.md` → Philosophy。

## 1. 工作流属于用户，不属于内核

对比常见路线：

| 路线 | 结果 |
|------|------|
| 内核堆功能 | 人人被迫同一套 Plan / TODO / 权限 UI |
| Pi | 内核只保「能跑 Agent」；工作流用扩展拼 |

口号：

> Adapt pi to your workflows, not the other way around.

二次开发的默认动作是 **加扩展 / 装包**，不是 **改 `interactive-mode.ts` 然后永远 rebase**。

## 2. 最小完备核心（Minimal Core）

「最小」不是简陋，而是**完备集尽量小**：

- 能对话、能调工具、能改仓库文件、能跑命令
- 能持久化会话、能选模型、能有体面的 TUI
- 能被扩展、能被嵌入

多出来的「协作仪式」（子 Agent、Plan、MCP 总线、全局权限弹窗）全部外置。

好处：

- 模型更不容易被内置 TODO / 复杂模式搞糊涂（官方明确说 built-in to-dos confuse models）
- 安全边界由部署环境决定，不假装内核已沙箱

## 3. 可组合的扩展面，而不是单一插件协议

Pi 提供**多层不同成本**的定制：

```
Themes / Prompt Templates   ← 几乎零代码
Skills                      ← Markdown + 可选脚本
Extensions (TS)             ← 完整能力：工具、钩子、UI、Provider
Pi Packages                 ← 打包分发上述资源
SDK / RPC / JSON            ← 嵌入与进程集成
Containerization            ← 部署隔离
```

哲学含义：**用合适的钉子钉合适的板**——改一句提示词不必写 Extension；要拦 `rm -rf` 才写钩子。

## 4. 事件可观察，钩子可参与

在 agent-core / harness 设计里：

- **Events**：观察已发生的事（做 UI、日志、遥测）
- **Hooks**：语义参与（改上下文、拦截工具、影响 compaction）

不要把「旁路观察」和「改写行为」混成一种回调。这对二次开发者很重要：扩展作者需要清楚自己是在「看」还是在「改」。

## 5. 会话是真相，运行时依赖可重建

Harness / durable 方向的核心判断：

- **会话日志**（消息、工具结果、树结构）应当可持久化、可恢复
- **工具实现、扩展、模型客户端**是宿主注入的运行时依赖——不必（也不该）完整序列化进会话文件

恢复会话 = 重放/加载日志 + **重新挂上**当前环境的工具与扩展。

这对「适合二次开发」极关键：你可以换工具实现、换沙箱，而不必换会话格式。

## 6. 供应链与确定性

根 README 的 supply-chain hardening 也是哲学的一部分：

- 依赖钉死版本
- lockfile / shrinkwrap 当真
- 默认 `npm install --ignore-scripts`
- 把依赖变更当代码审查

Agent 工具链本身就是高权限软件；Pi 选择在**工程供应链**上偏偏执，而不是在产品里堆假权限 UI。

## 7. 开放训练数据的文化立场

官方鼓励分享 OSS 上的 coding agent sessions（Hugging Face 等）。  
哲学延伸：**真实工作流数据 > 玩具 benchmark**。学习 Pi 时也会碰到「session 格式为什么要稳定、可分享」的设计约束。

## 设计张力（要接受的取舍）

| 收益 | 代价 |
|------|------|
| 内核干净 | 很多「开箱功能」要自己装或写 |
| 无内置权限弹窗 | 新手可能低估风险 |
| 无 MCP | 要接 MCP 需自建或装包 |
| 扩展能力极强 | 扩展与 Pi 同权（能碰文件系统）——信任模型要清醒 |
