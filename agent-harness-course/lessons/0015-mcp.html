MCP 深潜：协议、哲学与桥接蓝图

第 13 课的比较表里，MCP 是 Pi 与其他三家分歧最大的一条划线。这一课把这条线挖到底：MCP 协议本身是什么、Pi 为什么刻意零实现、作者自己的反方论证、以及——如果你想接——一张标注了每个决策点的桥接蓝图。

本课核心问题：MCP 是什么？Pi 为什么刻意不内置？以及最重要的判断框架——什么时候一个 Harness 应该把 MCP 放进 Core？

一、这张图要解决什么问题

MCP（Model Context Protocol）是当前工具生态的事实协议，但 Pi 一个字都没实现——这句话同时引出三个问题：协议本身长什么样（不搞懂就没法评判取舍）？"零实现"是懒还是哲学？（第 8 课 Minimal Core 的压力测试续集）如果你真需要 MCP，接缝在哪？这张图把三者画在一张画布上，并诚实标注：桥接部分是设计推断，Pi 当前不存在。

二、MCP 三十分钟速成【公开资料】

公开资料以下按 Model Context Protocol 规范（modelcontextprotocol.io，spec 仍在演化，请以最新版为准）：

角色分工：Host 是嵌入 MCP Client 的应用（比如一个 Coding Agent）；Client 与 Server 保持 1:1 会话；Server 是暴露能力的服务——可以是本地子进程（stdio 传输），也可以是远端服务（Streamable HTTP 传输）。底层消息全部是 JSON-RPC 2.0。

三种原语：tools（模型可调用的函数——对应第 3 课的 toolCall 机制）、resources（可读取的数据）、prompts（预置提示词模板）。连接时双方先做 capability 协商（"我有哪些工具"）。

它解决的问题：工具生态的 N×M 问题——没有协议时，M 个 Agent 要各自适配 N 个工具源；有了协议，工具作者写一次 Server，所有支持 MCP 的 Agent 都能用。这正是第 13 课"生态协议放哪条线"的背景。

三、如何从图上读懂 Pi 的立场

源码事实：零实现。在 packages/*/src 全库 grep modelcontextprotocol / mcp-server / mcp client——零命中。工具生态的大门不是 MCP，而是第 8 课的 registerTool（extensions/types.ts:1762）与 80+ 个扩展示例。

文档立场：learn-pi 的《刻意省略》（fork 自带导读，转述自官方 Philosophy）："优先用带 README 的 CLI 工具（配合 Skills），或自己写 Extension 加 MCP"；"真要 MCP，扩展层实现即可，不必等内核。"——注意这句话已经回答了本课标题的一半：Pi 认为接缝已足够，MCP 属于 Harness 层的选择。

文档反方论证的正面呈现：作者 Mario Zechner 的博文《What if you don't need MCP at all?》（2025-11-02，learn-pi 中链接）给出三条批评，值得逐条记住：

  1. 上下文开销：Playwright MCP 有 21 个工具、13.7k tokens 的描述；Chrome DevTools MCP 26 个工具、18k tokens。"That many tools will confuse your agent."——对照第 7 课的渐进披露：MCP 的工具列表是"一次性全量注入"的，与 skills 的哲学相反。
  2. 可组合性："Results returned by an MCP server have to go through the agent's context to be persisted to disk or combined with other results."——工具结果必须流经模型上下文才能被组合，而 shell 管道不用。
  3. 难扩展：改一个 MCP Server 的输出格式 = 读别人的代码库；改自己的 CLI 脚本 = 改十行。

他的替代方案：四个 bash 可调的 Node 脚本（nav/eval/screenshot/cookies）+ 一份 225 tokens 的 README，让模型直接 eval.js 操作浏览器。核心信念一句话："Bash and code are composable."——这正是 Pi "工具就是进程与文件" 哲学的极端版。

作者也承认的反面：现有 MCP Server 本身"both are fine"，问题在覆盖面过大；skills 的渐进披露他"love it"。所以这不是"谁是坏人"的故事，而是两条真实的工程权衡曲线：生态复用 vs 上下文预算。

四、判断框架：什么时候把 MCP 放进 Core？

把第 12 课的三箱法 + 第 13 课的划线收拢成三个问题，依次问：

  1. 生态需求密度：你的用户每周都要接新的 MCP Server 吗？如果偶发，扩展桥（甚至直接写 CLI 工具）够了；如果高频，内置 Client 的固定成本才开始摊薄。
  2. 信任模型：每个 stdio MCP Server 都是一个以你的 OS 权限运行的子进程（图上虚线框——第 9 课的边界）。Core 内置意味着 Core 要定义"哪些 Server 默认可信、如何审批、如何沙箱"——这正是 Pi 刻意外包的决策面。没有信任策略的内置只是把风险改名为功能。
  3. 维护预算：spec 在演化、transport 在演化（stdio → HTTP）、版本协商要跟。内置 = Core 签下长期维护合同。Pi 的答案：不签；Claude Code/Codex 的答案：签。两者都自洽，因为各自的用户密度与维护预算不同。

三问之后，你会得到与 Pi 相同或不同的结论——重要的是你做过这三问，而不是结论与谁一致。

五、动手蓝图：用扩展桥接 MCP（选做练习）

推断如果结论是"我需要"，接缝已经存在。桥的骨架（约 80 行真代码，留作选做练习——对照 毕业练习 的 hooks.py）：

# mcp-bridge.ts —— 一个普通 Pi 扩展（设计蓝图【推断】，非当前实现）
export default (pi) => {
  const clients = config.servers.map(s => connect(s))     // JSON-RPC 会话
  pi.on("before_agent_start", async () => {
    for (const c of clients) {
      for (const t of await c.listTools()) {              // capability 协商
        pi.registerTool(toMcpTool(c, t))                  // 动态注入菜单（第 3 课）
      }
    }
  })
  pi.on("tool_call", async (e) => {
    if (!e.toolName.startsWith("mcp:")) return            // 只处理桥的工具
    const out = await clients.get(e.server).callTool(...) // 转发 JSON-RPC
    return { content: out }                               // 走普通 toolResult 回填
  })
}

注意两点与课程前文的呼应：工具经 registerTool 进菜单（第 8 课注册面）；执行结果走普通 toolResult 回填（第 3 课）——桥不需要改 Core 的任何一行，这正是 Minimal Core 的自证。别忘了 Trust 门禁（图上粉色节点）：项目级的桥扩展只有被信任才会加载。

六、七问（MCP-in-Pi 专场）

  1. 解决什么问题？MCP 解决工具生态的 N×M 适配；"不内置"解决 Core 表面积与信任模型问题。
  2. 没有它会怎样？Pi：工具生态靠 CLI+skills+扩展（第 7/8 课）；需要者写桥。
  3. 输入是什么？Server 的 capability（工具清单）与 JSON-RPC 调用/响应。
  4. 输出是什么？动态注册的菜单项 + 普通化的 toolResult。
  5. 由谁控制？协议：spec；会话：Client；加载：Trust；策略：你的扩展代码。
  6. 和前概念的关系？它是第 13 课"生态协议划线"的深潜，也是第 8 课注册面 + 第 9 课信任边界的联合应用。
  7. Pi 在源码哪里实现？源码不实现（全库 grep 零命中）；接缝在 extensions/types.ts:1762；立场文档 learn-pi/01-设计哲学/刻意省略.md。

八、这张图在整个体系中的位置
