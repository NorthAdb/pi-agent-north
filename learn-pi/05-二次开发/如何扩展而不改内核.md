# 如何扩展而不改内核

## 原则

1. **先搜 examples**，再写代码  
2. **先 Skill/Prompt，后 Extension**（能轻则轻）  
3. **先观察事件，后拦截行为**  
4. **用 package 分发**，避免每人一份私改内核  
5. **改内核前先问**：能否 `registerTool` / `on(...)` / 自定义 ResourceLoader / 自定义 provider？

## 路径 A：项目级工作流（最常见）

1. 在项目放 `AGENTS.md` 写清规范  
2. 加 skills / prompt templates  
3. 需要强制约束时加 extension（例如禁止未提交就 exit、危险命令确认）  
4. 团队用 `pi install` 装内部 git/npm 包  

验证：新同事 clone 项目 + 装包后，行为一致。

## 路径 B：用户级生产力

资源放在用户配置目录（`piConfig.configDir`，默认与 `.pi` 相关路径，详见 settings 文档）。  
适合个人快捷键、主题、通用 skills。

## 路径 C：嵌入式产品

1. 依赖 `@earendil-works/pi-coding-agent`（或 workspace 源码）  
2. `createAgentSession` 装配模型与工具  
3. 关掉不需要的 discovery，注入自己的 extensions  
4. UI 完全自绘，只消费事件  

参考：`examples/sdk/12-full-control.ts`。

## 路径 D：安全加固

按威胁模型选：

| 手段 | 文档/例子 |
|------|-----------|
| 确认门扩展 | `confirm-destructive.ts`、`permission-gate` |
| Docker 整进程 | `docs/containerization.md` |
| Gondolin 微 VM | 同文档 + `examples/extensions/gondolin` |
| OpenShell | 同文档 |

不要只做「提示模型小心」——模型会忽略；要在工具钩子或 OS 边界强制。

## 路径 E：自定义模型供应

1. 标准 API → `models.json` / 内置 provider 配置  
2. 非标 → extension `registerProvider`  
3. 本地 llama.cpp → 官方 `docs/llama-cpp.md`

## 什么时候才该改内核

- 发现扩展 API 的真实缺口，并准备 **PR 回上游**  
- 研究性改动循环语义（应先读 harness/hooks 文档）  
- 修复 bug（如遗漏字段导致 build 失败）  

改内核时遵守 `AGENTS.md`：小步、测准、changelog 规范、不要误伤其他 agent 会话的 git 状态。

## 推荐一周练习（二次开发向）

| 日 | 练习 |
|----|------|
| 1 | 跑通源码 `pi-test`，完成一次真实小重构 |
| 2 | 写 skill + prompt template |
| 3 | 写 extension：给所有 `bash` 打日志 |
| 4 | 写 extension：拦截匹配危险模式的命令 |
| 5 | 把 2–4 打成 package 并 `pi install` 到另一目录验证 |
| 6 | SDK minimal → 自定义 tool |
| 7 | 读 `agent-loop.ts` 事件路径，画自己的序列图 |

## 检查清单（发版前）

- [ ] 无扩展时核心路径仍可用  
- [ ] 扩展失败是否有明确错误（不要静默）  
- [ ] 不在扩展里硬编码密钥  
- [ ] 文档写明信任与权限假设  
- [ ] 若改会话格式，有迁移/兼容策略
